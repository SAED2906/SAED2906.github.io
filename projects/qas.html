QAS — Quantum Architecture Search

QAS is a Python framework for evolutionary architecture search, built mainly for quantum circuits. The search engine is separate from the problem it solves, so the same unchanged engine runs quantum kernel search, VQE and variational classifiers, and also problems with no quantum content at all.

StatusResearch framework, in active development
Tools & technologiesPython / NumPy / HierarQcal / PennyLane

Why the engine is separate

Most architecture search tools for quantum circuits are written around one objective, usually VQE. Asking a different question means rewriting the search loop: selection, mutation, diversity control, checkpointing. QAS splits those apart. The engine decides how candidates compete and survive. A small problem definition says what a candidate is and how good it is.

A core with four contracts

The core is deliberately small. It defines Genome, Score, CostFunction and EvolutionarySearch. A Genome describes how a candidate is sampled, mutated, compared and serialised. A CostFunction has one required method: it takes a genome and returns a Score, which holds a fitness and any metrics worth recording.

The core imports NumPy and joblib and nothing else. It has no way of knowing whether it is optimising a circuit, a vector or an expression, and quantum dependencies are only pulled in by the optional modules built on top of it.

fitness-contract.pyPython 
class MyCost(CostFunction):
    def evaluate(self, genome: Genome) -> Score:
        ...  # problem-specific evaluation
        return Score(fitness=value, metrics={"my_metric": value})

One search, different problems

Changing the problem changes the cost function and, where the data differs, the encoding names. The search itself stays as it is. The block below drives a kernel search or a ground-state search depending on which cost function is passed in.

same-engine.pyPython 
# Quantum kernel search: cross-validated SVM accuracy
cost_fn = SparseKFoldCVCost(X, y, encoding_funcs, n_folds=3, sparse_factor=0.3)

# Variational search: energy of a Hamiltonian
cost_fn = GroundStateEnergyCost(hamiltonian)

search = qas.EvolutionarySearch(
    genome_cls=LayeredCircuitGenome,
    cost_fn=cost_fn,
    space_kwargs={
        "library": library,
        "n_qubits": 8,
        "enc_names": enc_names,  # [None] when there is no data
        "min_layers": 3,
        "max_layers": 12,
    },
    pop_size=25,
    n_generations=100,
    n_jobs=2,
    live_port=8765,
)
result = search.run()

Circuits as genomes

The circuit genome in the contributed modules is built on HierarQcal. A candidate is a stack of layers. Each layer is a motif (cycle, pivot, mask or unmask) with its own parameters, and most carry a gate. Because the patterns are relative rather than tied to particular wires, a circuit found at one qubit count can be rebuilt at another.

Each parametrised gate carries either a free trainable angle or a data-encoding function, chosen per gate. One genome type therefore covers both kernel circuits, where gates encode data, and variational circuits, where they hold trainable parameters. Kernel circuits are built as a feature map followed by its adjoint, so the genome can also reverse itself exactly, including the order of gates inside a layer that sweeps several qubit pairs.

What the search does

Each generation, candidates are mutated and evaluated in parallel with joblib. Selection mixes fitness with structural distance so the population does not collapse onto a single design, elites are carried over, and when progress stalls a plateau step reinitialises most of the population. Runs write checkpoints and per-generation logs to disk.

With a live port set, the search also streams events over TCP as newline-delimited JSON: fitness, diversity, plateaus, and the genome behind each new best. Any client can follow a run, and a small monitor script plots it without knowing what the problem is.

Problems included

Quantum kernel search scores a circuit by the cross-validated accuracy of an SVM on its kernel matrix, or by kernel-target alignment, with sparse variants that evaluate only a fraction of the kernel entries. This is where the framework started. It grew out of MSc research on evolutionary quantum kernel search at Stellenbosch University and has been run on the CHPC Lengau cluster.

VQE scores a circuit by the energy it reaches on a Hamiltonian, with the circuit structure itself being searched rather than a fixed ansatz. Transverse-field Ising and MaxCut Hamiltonians are included, along with a helper that turns an arbitrary classical cost function over bitstrings into a diagonal Hamiltonian, so a new combinatorial problem needs a function rather than a new module.

The variational classifier uses the sign of a Pauli-Z expectation as the prediction, with no SVM anywhere, and reuses the VQE evaluation code once per data point. Outside quantum computing, the tutorial evolves plain vectors and symbolic expressions with the same engine, which is the quickest way to see that the core makes no circuit-specific assumptions.

An example run

As a check on the VQE module, a search over 8-qubit circuits for the ground state of a periodic transverse-field Ising model (J = h = 1) reached an energy of −9.9991. The exact value is −10.2517. The best circuit contained no entangling gates, and for this Hamiltonian the lowest energy any unentangled product state can reach is exactly −10.0000. The search came within 0.001 of the best that is possible without entanglement.

The remaining 0.25 is correlation energy, which needs entangling gates. Why entangled candidates did not survive is not settled. A likely reason is that one entangling gate makes an otherwise well-tuned circuit worse before the rest of it can adapt, so it loses selection first. Keeping such lineages alive long enough to pay off is the main open question for the selection step.

Current limits and next steps

A run cannot yet be resumed from a checkpoint. Restoring the population, scores and random state is the next engine feature. The default structural distance is binary, so it cannot see features such as how many layers are entangling, which is the feature the example above depends on. Selection is single-objective, although a Pareto helper already exists. The live feed is plain TCP, and a WebSocket bridge for browser dashboards is planned. Packaging, documentation and test coverage for a public release come alongside these.
